# 分账 Bug 的技术分析

> 提交说明（题目要求的第 1、3、4 项）在 `code/README.md`；本文写第 2 项的推导过程、边界契约和方案取舍。

## 1. 根因：三个问题叠在一起

原实现只有一行：

```python
return [round(pool_cents * w / total) for w in weights]
```

| 问题 | 后果 |
|---|---|
| **逐项独立取整** | 每个人的误差在 ±0.5 分之间随机分布，n 个人不会互相抵消，`sum` 可能比池额多也可能少 |
| **Python 的 `round()` 是银行家舍入** | `round(0.5) == 0`、`round(2.5) == 2`，连「谁该进位」的直觉都不成立 |
| **`/` 是浮点除法** | 金额超过 2^53 分后丢精度，实测 10^18 量级会多发 25 分 |

第一、二条决定了「偶然」和「必然」：`pool=100, weights=[1,2,3]` 恰好整除，永远是对的；
`pool=100, weights=[1]*6` 每次都是 102。所以不是「偶尔抖动」，而是**确定的错误**，只是被整除的样例掩盖了。

## 2. 为什么不能「发现差额再补一下」

最省事的改法是算完 `sum`，把差额从某个人身上加/减掉。问题是：

* 差额可能是 `+2`（`100 / [1]*6` → 102），也可能是 `-1`（`10000 / [1,1,1]` → 9999），方向不定；
* 差额要补给的如果是**已经拿到 0 分**的人，会凭空多出一个中奖者；
* 减的时候可能把某人减成负数（池子小于人数时更常见）。

这类补丁能通过手写的几个样例，但换来的是一个不可解释的规则。要的是**先定规则、再算钱**。

## 3. 采用的方案：最大余数法（Hamilton / Hare quota）

```
total = Σw
对每个人 i：
    q_i, r_i = divmod(pool * w_i, total)      # 整数部分 + 余数
leftover = pool - Σq_i                        # 还没分出去的零头
把 leftover 个 1 分，发给 r_i 最大的那几个人
```

### 正确性（三行证明）

1. `q_i = ⌊pool·w_i / total⌋` ⇒ `Σq_i ≤ pool·Σw_i/total = pool`，所以 `leftover ≥ 0`；
2. `leftover = pool - Σ⌊x_i⌋ < Σ(x_i - ⌊x_i⌋) + 1 ≤ n` ⇒ `0 ≤ leftover < n`，**补发不会超出人数**；
3. 补完之后 `Σshare_i = Σq_i + leftover = pool`。∎

同时 `⌊x_i⌋ ≤ share_i ≤ ⌊x_i⌋ + 1`，即**每个人与精确值的偏差都小于 1 分**——这是能拿到的最公平结果：
任何保证总额精确的整数分配，都必然有人差将近 1 分，不可能所有人同时精确。

### 全程整数

`divmod(pool_cents * w, total)` 里没有 `/`，所以 10^18 分也不会丢一分钱，顺带修掉了浮点精度问题。

## 4. 平局规则（这是「换一个人是否可行」的答案）

余数相同时按「**权重大 → 下标小**」补分。三个理由：

1. **确定性**：同样的输入永远得到同样的输出，重算/对账不会漂移；
2. **可解释**：客服被问「为什么他多拿 1 分」时，能回答「他余数最大，并列时权重更高」；
3. **可替换**：换成「按下单时间」「按用户 ID」都行，只要**固定下来并写进对账文档**。
   真正的风险不是「谁多拿 1 分」，而是**规则没定死**——同一批数据今天算和明天算结果不同，那才是灾难。

举例：`10000 / [1,1,1]` → 每人 `3333` 余 `1`，三人余数并列 → 下标 0 补 1 分 → `[3334, 3333, 3333]`。

## 5. 输入契约

| 输入 | 行为 | 理由 |
|---|---|---|
| `pool ≥ 0`，权重非负、至少一个 > 0 | 正常分配，`sum == pool` | 主路径 |
| `pool == 0` | 全 0 | 没钱可分 |
| `weights` 为空 + `pool == 0` | `[]` | 合法空集 |
| `weights` 为空 + `pool > 0` | `ValueError` | 没有任何收款人，钱无处可去，必须让调用方知道 |
| 权重**全 0** + `pool > 0` | **平分兜底** | 见下 |
| 权重含 0（非全 0） | 该用户得 0 | 权重即贡献 |
| 负数池子 / 负数权重 | `ValueError` | 违反「金额是整数分、贡献非负」的领域约束 |

**「全 0 权重」为什么选择平分而不是抛错：** 这条硬规则是「分完必须正好等于池额」。
如果这里抛异常，那么这一类输入就永远拿不到合规的结果，规则在最极端的情况下反而失守。
平分是唯一中立的规则（大家都 0 贡献 ⇒ 无法区分优劣），且总额精确。
如果产品认为「无人达标当天不发」，正确做法是**调用方把 pool 置 0**，而不是让分配函数去猜。

## 6. 其他方案对比

| 方案 | 是否满足总额精确 | 评价 |
|---|---|---|
| 各自 `round()`（原实现） | ❌ | 误差不抵消 |
| 最大余数法（采用） | ✅ | 偏差 < 1 分，规则直观，O(n log n) |
| 除数法（Webster/Sainte-Laguë） | ✅ | 更偏向小权重方，需迭代，解释成本高 |
| 逐分发放（每人依次 +1 分直到发完） | ✅ | O(pool) 太慢；且等价于「按下标轮询」，对大权重不公平 |
| `Decimal` + 四舍五入 | ❌ | 只解决精度，不解决「取整后总和必须相等」 |
| 最大余数法 + `Decimal` | ✅ | 精度上过度设计，整数运算已经足够 |

## 7. 测试策略

不写「几个样例断言等于某个数组」，因为数组一改测试就废，而且覆盖不了余数组合。改为：

1. **唯一不变量**：`sum(result) == pool`（唯一真正重要的性质）；
2. **穷举**：池子 0–120 × 3 人权重 0–4（15 125 组）+ 4 人版本 —— 目标是覆盖所有余数组合；
3. **随机**：固定种子 500 组，池子 10^7、人数 50，覆盖规模化后的整除边界；
4. **性质断言**：`floor ≤ share ≤ floor+1`、确定性、不改入参；
5. **边界**：0 分、1 分分给 1000 人、全 0 权重、空列表、负数、10^18。

同一份测试用环境变量切换被测模块，保证「旧代码失败 / 新代码通过」跑的是**完全相同的用例**，
而不是「失败一套、通过另一套」——否则证明不了任何事。

## 8. 遗留风险（上线前值得确认）

* **作弊/刷时长**：权重来自「合格采集秒数」，分账只保证算得对，不保证权重本身可信；
* **对账快照**：`weights` 如果在分配后被修改（补录、申诉改判），当天结果就对不上了，
  建议分配时把 `weights` 快照一起落库；
* **幂等**：每日任务重跑必须得到同一结果（当前实现满足），但调用方要防止「跑两次发两次钱」。
